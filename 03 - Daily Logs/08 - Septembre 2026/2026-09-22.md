## 💡 Découverte du jour

En recherche modèles PartSmart, le code catalogue affiché (`catalogCode`) ne coincide pas toujours avec l’identifiant utilisé pour ouvrir la fiche (`catalogId`) — Whirlpool Legacy répond en `whi`, Maytag en `whtst` pour les mêmes familles de numéros de modèle.

## ✅ Réalisations

### Fiche produit catalogue — stock par succursale
*Les données existaient déjà côté API ; il manquait seulement l’affichage retiré plus tôt.*

- Restauration du bloc « quantité disponible » avec les huit succursales et le total — même ordre qu’en magasin / ERP
- Mise en page en deux colonnes sur grand écran : infos et liste de souhaits à gauche, stock et achat empilés à droite
- Masquage du bloc pour les pièces catalogue uniquement (pas d’inventaire succursale)
- Conservation du badge de disponibilité actuel (« en stock », délai fournisseur, catalogue) sans revenir au libellé « rupture »

### Recherche header — superposition UI
*En ouvrant les suggestions de recherche depuis une fiche produit, le badge vert passait par-dessus le menu.*

- Retrait d’un empilement CSS inutile sur le badge coin haut-droit — le panneau de recherche du header repasse au premier plan

### Recherche par modèle — filtre fabricant
*Le filtre comparait un mauvais code catalogue : résultats vides sans message d’erreur.*

- Alignement des codes PartSmart (`whi` pour Whirlpool, `whtst` pour Maytag, `fri` pour Electrolux) avec ce que renvoie l’API modèles
- Logique de parsing et filtrage extraite et couverte par tests unitaires
- Smoke local : GE sans hits sur les requêtes testées — filtre laissé sur `ge` en attendant un modèle de référence côté catalogue

## 🧠 Ce que j'ai appris

- **Même z-index, ordre du DOM** : quand le header et un élément de la page ont le même niveau d’empilement, ce qui est rendu plus tard dans la page peut masquer les menus du header ; inutile de monter le z-index du contenu si le positionnement absolu suffit dans la carte.
